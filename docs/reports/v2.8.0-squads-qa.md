# QA: v2.8.0 squads and v2.9 devices readiness

Scope: issue #92, agent 2 zone only (`.github/workflows`, `backend/test`, `docs/reports`, `bench`).
Product code, versions and releases untouched. Feature under test: PR #91 (`48e45a4`, v2.8.0).

## Coverage

`backend/test/squads.e2e-pg-spec.ts` (4 PostgreSQL e2e tests):

1. **CRUD and persistence** — empty list, create with `trafficLimit`/`expiresAt`, list with
   `_count.users`, `GET :id` with the member list, `PATCH` (rename, limit, expiry, disable),
   re-read after persistence, `DELETE` → 404 on a repeated read.
2. **RBAC** — anonymous `GET`/`POST` → 401; `USER` `GET`/`POST`/`PATCH`/`PATCH members`/`DELETE`
   → 403 with no mutation; `OPERATOR` full access.
3. **Membership** — `PATCH /squads/:id/members` replaces the whole member set (not additive);
   `GET :id` and `_count.users` reflect it; `PATCH /users/:id` with `squadId` attaches and with
   `null` detaches; an empty `members` body clears the squad.
4. **Tenant scope** — an `OPERATOR` in org A can attach their own user but gets 404 when updating
   or reading an org B user; that user's `squadId` stays untouched and the squad member list
   contains only the in-scope user.

`backend/test/devices.e2e-pg-spec.ts` — 2 tests registered as **pending** (`describe.skip`), because
`POST /api/devices/bind` ships in v2.9.0 and is not present in v2.8.0. They cover binding by
`subscriptionToken` (including an unknown token), the device limit from `DEVICE_LIMIT` (default 3)
and `BLOCK` status after the limit is exceeded. Remove the `.skip` when the v2.9 API lands.

`bench/scenarios/smoke.js`: `/api/squads` added to `PROTECTED`, alongside `/api/config-profiles`
from PR #94.

Config profiles from item 2 of #92 were already delivered and closed in #90 / PR #94
(`docs/reports/v2.7.0-config-profiles-qa.md`); no duplicate work here.

## Notes / follow-ups (product code outside this zone)

- Squads are global and have no `organizationId`. `PATCH /squads/:id/members` accepts user ids from
  any tenant when called by an ADMIN or OPERATOR, so a broad operator can put users from another
  organization into the same squad. Per-user updates remain tenant-scoped (test 4). If squads are
  meant to be tenant-local, this needs a product change and a stricter e2e assertion.
- `GET /api/squads/:id` includes member emails for the whole squad; combined with the point above,
  an operator can see users outside their organization through this endpoint. Reported for the
  product owner rather than encoded as expected behaviour.
- Live smoke on https://msc.h2onetwork.pro runs in CI; authenticated checks (including node ONLINE)
  are skipped until `LIVE_ADMIN_EMAIL`/`LIVE_ADMIN_PASSWORD` secrets are provided.
