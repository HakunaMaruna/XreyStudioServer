# Хосты и готовые рецепты

Хост — это адрес назначения с портом, именем (SNI) и путём. Хosts используются в правилах роутинга и могут быть **привязаны к подключению**, чтобы панель сразу подставила SNI/путь и публичный адрес в ссылку подписки.

Для дефолтного подключения, создаваемого при установке ноды, SNI равен домену
ноды из CONTROL DNS (в панели это называют «selfSNI»; в Xray отдельного ключа
для этого нет — используется `tlsSettings.serverName`). См.
[онбординг ноды](node-onboarding.md#selfsni-и-сайт-заглушка).

## Как создать хост

1. **Инфраструктура → Хосты → Новый хост**.
2. В поле **«Готовый рецепт»** выберите один из пресетов — он автоматически заполнит порт, SNI, путь и заметку. Можно выбрать **«Свои настройки»** и задать всё вручную.
3. Укажите **адрес** (домен ноды или CDN) и, если нужно, поправьте остальные поля.
4. Сохраните. В таблице появится бейдж рецепта и подсказка по DNS.

## Готовые рецепты

| Рецепт | Что задаёт | Когда использовать |
| --- | --- | --- |
| **VLESS Reality (один port)** | TCP + Reality, SNI из настроек Reality | Один выделенный порт, маскировка под обычный HTTPS |
| **Общий порт 443 по SNI** | TCP + TLS, уникальное имя | Несколько сервисов на одном 443; запрос без имени уходит на дефолтный |
| **VLESS WebSocket за CDN** | WS + TLS, путь `/ws` | Когда напрямую доступен только 443 и нужен CDN |
| **Hysteria2 (UDP)** | QUIC + TLS, отдельный UDP-порт | Общий порт по SNI не работает — UDP не делится |
| **Trojan over TLS** | TCP + TLS | Классический вариант с паролем-токеном подписки |
| **Decoy-сайт / fallback** | TCP + TLS, «чужой» домен | Заглушка для чужих подключений, чтобы не светить панель |

Идеи подсмотрены в `Mistgate/mistgate` (общий 443 по SNI, decoy) и `remnawave/backend` (пресеты под протоколы) — оба под AGPL-3.0, реализовано самостоятельно.

## DNS

Рецепт показывает нужную запись в карточке хоста:

- `A` — домен ноды указывает на IPv4;
- `CNAME` — домен указывает на другое имя;
- для CDN обязательно **DNS only** (без прокси), иначе TLS-хендшейк не дойдёт до ноды.

Панель не проверяет запись автоматически — добавьте её там, где хранится DNS домена.

## Как это работает вместе с подключением

1. Создайте хост по рецепту.
2. В таблице хостов нажмите **«Привязать к подключению»** → выберите inbound.
3. Бэкенд обновит у подключения:
   - `sni` и `path` из хоста;
   - `transport` и `security` из рецепта;
   - `settings.publicHost` = адрес хоста.
4. Нажмите **«Применить»** на ноде — новая конфигурация уйдёт агенту.
5. Откройте страницу подписки: ссылка на подключение теперь содержит адрес хоста и нужные параметры (например `?type=ws&security=tls&path=%2Fws&sni=...`).

Если хост привязан к inbound с типом `userId`, пользователь увидит его в своей подписке сразу после применения конфигурации.

## Пример через API

```bash
TOKEN=$(curl -sS -X POST https://msc.h2onetwork.pro/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.com","password":"..."}' | jq -r .accessToken)

# список рецептов
curl -sS https://msc.h2onetwork.pro/api/hosts/recipes/list -H "Authorization: Bearer $TOKEN"

# хост по рецепту
curl -sS -X POST https://msc.h2onetwork.pro/api/hosts \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"address":"cdn.example.com","port":443,"recipe":"ws-cdn","sni":"cdn.example.com","path":"/ws"}'

# привязка к подключению
curl -sS -X POST https://msc.h2onetwork.pro/api/hosts/<host-id>/apply-to-inbound \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"inboundId":"<inbound-id>"}'
```
